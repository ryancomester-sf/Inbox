# Inbox hover-behaviour prototype

A plain HTML/CSS/JS rebuild of the Serviceform Lite inbox, extracted from
page snapshots so it can be edited directly and used as a base for
prototyping the ticket-list hover/select/open behaviour.

## `inbox-prototype.html` — the single-file version

**This is the one to open and work in.** All four captured states,
every stylesheet, every image, and the interaction JS are inlined into
one ~4MB HTML file — no server, no asset folder, just open it in a
browser or editor. A small tab bar at the top switches between states;
switching swaps in that state's own real CSS (dash vs. dev builds
aren't quite identical, so each state keeps its own copy rather than
sharing one that would render either the baseline or the others
slightly wrong).

It's generated by `build_single.py` from the multi-file version below
— re-run that script any time you regenerate `index.html` /
`states/*/index.html` and want the single file to pick up the change.

```bash
python3 build_single.py
```

## The multi-file version

There are four captures in total, spread across separate folders with
their own asset files — useful for diffing real markup/CSS file by
file. Open **`states.html`** for a linked index of all of them:

| Page | Source | What it shows |
| --- | --- | --- |
| `index.html` | `Inbox - Serviceform.mhtml` (production, `dash.serviceform.com`) | baseline — ticket list + a ticket already open |
| `states/list/index.html` | `Inbox - Serviceform - list.mhtml` (dev) | plain inbox list, nothing selected |
| `states/selected/index.html` | `Inbox - Serviceform - selected.mhtml` (dev) | a row checkbox-selected, bulk action bar showing |
| `states/open-ticket/index.html` | `Inbox - Serviceform - open ticket.mhtml` (dev) | full reading pane + contact panel open |

## Running it

Any static file server works, e.g. from the **project root** (one level
up from this folder, so the `states/*` pages can reach their assets):

```bash
python3 -m http.server 4173
```

then open `http://localhost:4173/prototype/states.html`.

## Layout

- `index.html` — the rendered DOM from the snapshot, cleaned up and
  re-pointed at local assets.
- `assets/css/app-*.css`, `base-font.css`, `fonts.css`,
  `misc-keyframes.css`, `spin-keyframe.css`, `toast-animations.css` —
  the real, unmodified production stylesheets pulled out of the
  snapshot. **Don't hand-edit these** — they're a reference for what
  ships today. `fonts.css` had one edit: a browser extension had
  injected fake `@font-face` rules pointing at
  `chrome-extension://...` font files into the captured page; those
  were stripped and replaced with real Inter / Roboto Mono loaded from
  Google Fonts in `index.html`.
- `assets/css/prototype.css` — loaded last; this is where new hover
  states and other prototype-only styling belongs.
- `assets/js/app.js` — the snapshot has no working JavaScript (it's a
  frozen DOM, not a running React app). This file restores minimal
  chrome interactivity (sidebar collapse, row selection) and is the
  intended home for the actual hover-behaviour implementation.
- `states/<slug>/index.html` + `states/<slug>/assets/` — the three
  dev-environment captures, each self-contained (own CSS/image copies,
  since each page load gets its own build hashes). They share
  `assets/css/prototype.css` and `assets/js/app.js` from the prototype
  root via a relative `../../` path.
- `build.py` — the one-off script that generated `index.html` and
  `assets/` from the original baseline `.mhtml`.
- `build_state.py` — the generalized version used for the three
  `states/*` captures; classifies each embedded CSS/image blob by
  content fingerprint (not by its per-capture-random filename hash) so
  re-running it against a fresh snapshot produces consistent names.
  Neither script is part of the running prototype — only needed to
  re-extract from a `.mhtml` file.

## Known gaps from the snapshots

- The floating Aircall call-widget (top right) was already
  collapsed/hidden in every capture, so its iframe was stubbed out
  rather than rebuilt — it pulled in ~1.5MB of unrelated third-party
  CSS/SVG for a widget that isn't visible anyway. Two small browser-
  extension overlay iframes (Jam) picked up by the capture were
  dropped entirely for the same reason.
- A handful of images/fonts referenced in the markup weren't loaded at
  capture time (browser cache hit, or off-screen), so those specific
  URLs still point at the live `serviceform.com` /
  `firebasestorage.googleapis.com` origins instead of a local file.
- Everything else is a faithful static copy: real markup, real
  production CSS (including the existing `.tli:hover` rule), real
  avatar/logo/favicon images.
